### 1.3 Semántica de los datos mensuales

Cada fila representa el **estado acumulado del proyecto al final del mes indicado**, no un incremento mensual. Es decir:

- La fila de `MAR 2025` ya incluye los compromisos hechos en ENE, FEB y MAR de 2025.

Por esto, para la serie mensual de ejecución se usan directamente los valores de cada mes sin acumular manualmente.

## 2. Diseño del ETL

### 2.1 Dos modos de lectura

El archivo se lee una sola vez con openpyxl (`read_only=True, data_only=True`) y los registros se separan en dos conjuntos:

| Conjunto | Filtro | Propósito |
|---|---|---|
| `records_corte` | `Mes == mes_corte` (MAR) | Comparaciones punto-en-tiempo: misma semana del año en todos los años |
| `records_mensual` | Todos los meses disponibles | Curva mensual de ejecución: trayectoria ENE–DIC por sector y año |

### 2.2 Normalización de sectores

```
raw_string
  → unicodedata.normalize('NFC', raw_string).strip().upper()
  → SECTOR_MAP.get(resultado, resultado)
```

**`SECTOR_MAP`** — cambios de nombre histórico:

| Nombre antiguo (MAYÚSCULAS) | Nombre canónico |
|---|---|
| `AGROPECUARIO` | `AGRICULTURA Y DESARROLLO RURAL` |
| `CIENCIA Y TECNOLOGÍA` / `CIENCIA Y TECNOLOGIA` | `CIENCIA, TECNOLOGÍA E INNOVACIÓN` |
| `COMUNICACIONES` | `TECNOLOGÍAS DE LA INFORMACIÓN Y LAS COMUNICACIONES` |
| `EMPLEO PUBLICO` | `EMPLEO PÚBLICO` |
| `PRESIDENCIA DE LA REPUBLICA` | `PRESIDENCIA DE LA REPÚBLICA` |
| `CONGRESO DE LA REPUBLICA` | `CONGRESO DE LA REPÚBLICA` |
| `JURISDICCION ESPECIAL PARA LA PAZ` / `JURISDICCIÓN...` | `SISTEMA INTEGRAL DE VERDAD, JUSTICIA, REPARACIÓN Y NO REPETICIÓN` |
| `FISCALIA` | `FISCALÍA` |
| `REGISTRADURIA` | `REGISTRADURÍA` |
| `PLANEACION` | `PLANEACIÓN` |
| `INFORMACION ESTADISTICA` | `INFORMACIÓN ESTADÍSTICA` |

### 2.3 Agregaciones y tablas destino

| Nivel | Operación | Tabla(s) destino |
|---|---|---|
| Total por año | `SUM(records_corte)` GROUP BY año | `ejecucion_historica` |
| Sector × año | `SUM(records_corte)` GROUP BY (año, sector) | `apropiacion_por_sector`, `compromisos_pct_por_sector`, `obligaciones_pct_por_sector`, `pagos_pct_por_sector` |
| Entidad (año actual) | `SUM(records_corte)` GROUP BY (sector, entidad) WHERE año = máx | `ejecucion_sectorial_entidades` |
| Sector × mes × año | `SUM(records_mensual)` GROUP BY (año, mes, sector) | `ejecucion_sectorial_mensual` |

### 2.4 Lógica de la serie mensual (`ejecucion_sectorial_mensual`)

Para cada (sector, mes) se calculan cuatro indicadores:

| Columna DB | Fuente | Meses disponibles |
|---|---|---|
| `pct_compromisos_2025` | % comp/vig del año actual (2026) | 1 a `mes_corte` (MAR=3); `NULL` para meses ABR–DIC |
| `pct_compromisos_2024` | % comp/vig del año anterior (2025) | Hasta el mes máximo disponible en el Excel |
| `pct_compromisos_prom` | Promedio de % comp/vig para años 2018–(anio_max–2) | Hasta el mes máximo disponible |
| `pct_compromisos_mejor` | MAX de % comp/vig histórico (mismos años que prom) | Hasta el mes máximo disponible |

> **Nota sobre los nombres de columna:** `pct_compromisos_2025` y `pct_compromisos_2024` son nombres fijos en el esquema heredado. Semánticamente representan "año del corte" y "año anterior", respectivamente. Para la Bitácora 2026-I (corte MAR 2026) estos campos contienen datos de 2026 y 2025.

## 3. Esquema de base de datos

### 3.1 Tablas actualizadas (sin cambio de esquema)

Todas las tablas ya existían en `db/schema.sql`. El ETL reemplaza su contenido con `DELETE + INSERT`.

**`ejecucion_historica`**

```sql
CREATE TABLE IF NOT EXISTS ejecucion_historica (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    bitacora_id         INTEGER REFERENCES metadatos_bitacora(id),
    vigencia            INTEGER NOT NULL,
    vigente_mmm         DECIMAL(12,3),
    compromisos_mmm     DECIMAL(12,3),
    obligaciones_mmm    DECIMAL(12,3),
    pagos_mmm           DECIMAL(12,3),

    inv_pct_gasto_total DECIMAL(5,2),   -- ⚠️ fuente externa: ver sección 5
```

Vigencias cargadas: **2018–2026** (ampliadas desde las 4 hardcodeadas anteriores).

**`apropiacion_por_sector`**, **`compromisos_pct_por_sector`**, **`obligaciones_pct_por_sector`**, **`pagos_pct_por_sector`**

### 3.2 Columnas agregadas por migración inline

## 4. Script ETL

**Archivo:** `etl/load_ejecucion_sectorial.py`

### 4.1 Ejecución

```bash
python etl/load_ejecucion_sectorial.py \
    --excel "BASES_BITACORA/2026/Marzo/6. EJECUCIÓN SECTORIAL/BASE DETALLE MENSUAL INVERSIÓN 2018-2026.xlsx" \
    --db db/pgn.db \
    --bitacora-id 1 \
    --mes-corte MAR
```

| Parámetro | Descripción | Por defecto |
|---|---|---|
| `--excel` | Ruta completa al archivo `.xlsx` | *(requerido)* |
| `--db` | Ruta a la base de datos SQLite | `db/pgn.db` |
| `--bitacora-id` | ID en `metadatos_bitacora` | `1` |
| `--mes-corte` | Mes del corte de reporte | `MAR` |

### 4.2 Flujo interno

```
load_excel()
  ├── records_corte   ← filas Mes == mes_corte
  └── records_mensual ← TODAS las filas (todos los meses)

load_db()
  ├── 3A. agg_totales(records_corte)       → DELETE + INSERT ejecucion_historica
  ├── 3B. agg_sectores(records_corte)      → DELETE + INSERT apropiacion/compromisos/obligaciones/pagos _pct_por_sector
  ├── 3C. agg_entidades(records_corte, anio_max) → DELETE + INSERT ejecucion_sectorial_entidades
  └── 3D. agg_mensual(records_mensual)     → DELETE + INSERT ejecucion_sectorial_mensual
```

### 4.3 Preservación de campos externos

`inv_pct_pib` e `inv_pct_gasto_total` no se pueden derivar de este archivo. El ETL los preserva para las vigencias que ya los tienen (leídos antes del DELETE) y los deja `NULL` para los años nuevos:

```python
pib_prev   = {r.vigencia: r.inv_pct_pib   for r in conn.execute(...)}
gasto_prev = {r.vigencia: r.inv_pct_gasto_total for r in conn.execute(...)}
# ... DELETE ...
# Al insertar:
(pib_prev.get(anio), gasto_prev.get(anio))   # None si el año es nuevo
```

## 8. Observaciones y decisiones

### 8.1 Corte MAR para comparaciones históricas

La tabla `ejecucion_historica` y las tablas de sector utilizan exclusivamente el corte de marzo. Esto permite comparar años al mismo punto del calendario. La apropiación "vigente" en marzo ya incluye todas las modificaciones presupuestales aprobadas hasta esa fecha, por lo que coincide con la apropiación vigente anual para la mayoría de los años.

### 8.2 Todos los meses para la curva mensual

La tabla `ejecucion_sectorial_mensual` usa los 148,214 registros completos (todos los meses) para construir la curva de ejecución ENE–DIC:

- **Año actual (2026):** datos reales ENE–MAR; `NULL` para ABR–DIC (meses no ocurridos).
- **Año anterior (2025):** datos reales ENE–DIC (cierre completo disponible en el Excel).
- **Promedio histórico (2018–2024):** calculado mes a mes sobre los años cerrados.
- **Mejor año (2018–2024):** máximo histórico por sector y mes.

### 8.3 Duplicidad de formas en Sector Homologado

El Excel contiene el mismo sector en MAYÚSCULAS (filas recientes) y en Título Case (filas anteriores). La deduplicación se resuelve con `unicodedata.normalize('NFC', raw).upper()` antes de aplicar el `SECTOR_MAP`. El resultado final es siempre MAYÚSCULAS, consistente con las demás tablas del esquema.

### 8.4 ETL debe ejecutarse por cada `bitacora_id`

El script `load_ejecucion_sectorial.py` inserta datos con `DELETE ... WHERE bitacora_id=?`. Esto significa que si existen múltiples bitácoras en `metadatos_bitacora`, el ETL debe ejecutarse **una vez por cada `bitacora_id`** que necesite datos históricos completos.

**Ejecución para la bitácora 2026-I (`bitacora_id=2`):**

```bash
python etl/load_ejecucion_sectorial.py \
    --excel "BASES_BITACORA/2026/Marzo/6. EJECUCIÓN SECTORIAL/BASE DETALLE MENSUAL INVERSIÓN 2018-2026.xlsx" \
    --db db/pgn.db \
    --bitacora-id 2 \
    --mes-corte MAR
```

`resolve_bitacora()` en la API siempre elige la bitácora más reciente por `corte_fecha DESC`. Si `bitacora_id=2` no tiene los datos, los endpoints de sector devuelven listas vacías aunque `bitacora_id=1` tenga datos correctos.

### 8.5 Fuente compartida entre Secciones 4 y 6

El archivo `BASE DETALLE MENSUAL INVERSIÓN 2018-2026.xlsx` es la fuente única para ambas secciones. La carpeta `4. EJECUCIÓN DE LA INVERSIÓN` del directorio `BASES_BITACORA` está vacía; los datos de Sec 4 provienen históricamente del mismo archivo de Sec 6.

### 8.6 Entidades vigencia 2026

Las 179 entidades cargadas para vigencia=2026 reemplazan las ~26 entidades hardcodeadas del `seed_data.py` (que eran de vigencia=2025). Ambas vigencias coexisten en la tabla con diferentes valores de `vigencia`.
